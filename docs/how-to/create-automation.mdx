Use an automation when a task should run more than once with the same owner, trigger, and output path.

## Before you start

Decide four things:

| Question | Why it matters |
| --- | --- |
| What should run? | The automation needs a stable task, not an open-ended discussion |
| Who owns it? | Ownership decides who should inspect failures and results |
| What starts it? | Choose schedule, manual dispatch, API, or webhook |
| Where should output go? | Choose chat output or tracked issue output |

If those answers are unclear, shape the work in Chat or an issue before automating it. Both are first-class task surfaces; choose the structure that fits the scenario.

## Create the automation

1. Open Automations.
2. Create a new automation.
3. Name the repeated job in plain language.
4. Choose the owner and agent or runtime that should execute it.
5. Write the prompt or job definition.
6. Choose a trigger.
7. Keep the default chat output, or explicitly switch to tracked issue output.
8. Save the automation.

Use a name that describes the actual work, such as "Prepare weekly agent work report" or "Check failed run backlog."

## Choose a trigger

Use a schedule for routine work. Use manual dispatch when an operator should decide when the task runs. Use API or webhook triggers when another system starts the work.

## Choose the output mode

New custom automations default to chat output. Keep it when operators should receive and continue each result through a conversation.

Switch to issue output when the result needs explicit assignment, status, review, artifacts, or follow-up work. Task importance, cost, or length does not force that choice, although a governed team policy may require issue fields.

## Understand what each run creates

Each real chat-output execution creates a separate Messenger conversation linked from that automation run. Rudder does not reuse an arbitrary existing Chat for every run.

Skipped or coalesced runs do not create empty conversations. If execution fails after chat output begins, the conversation keeps visible partial or fallback evidence so the failure is not hidden behind an empty unread thread. Tracked issue output creates an execution issue and then follows the normal issue assignment, run, and review lifecycle.

## Test the automation

Run the automation once before relying on it.

Check:

- the run starts from the expected trigger
- the selected agent or runtime receives the right context
- the result appears in the expected issue or chat
- failures are visible from the automation run history
- a failed chat-output run leaves inspectable evidence rather than an empty thread
- the owner knows where to inspect future runs
