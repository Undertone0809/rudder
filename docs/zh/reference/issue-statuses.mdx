<a id="definition" />

状态用来表示任务接下来需要哪类行动。它不能代替负责人、评审人或书面上下文。

<a id="states" />

## 状态速查

| 状态 | 含义 | 常见下一步 |
| --- | --- | --- |
| 待整理（`backlog`） | 仍需确定范围、优先级、负责人或验收条件 | 把任务写清楚 |
| 待办（`todo`） | 一个负责人不需要更多决定就能开始 | 负责人开始 |
| 进行中（`in_progress`） | 负责人正在处理 | 产出结果 |
| 阻塞（`blocked`） | 必须先等人、依赖、权限或外部事件 | 写清并解除阻塞 |
| 评审中（`in_review`） | 结果已经可以独立判断 | 评审人决定 |
| 已完成（`done`） | 结果已经被接受 | 需要时再建后续任务 |
| 已取消（`cancelled`） | 工作被主动停止，而且没有已接受结果 | 任务再次需要时才重新打开 |

<a id="constraints" />

## 会影响流程的规则

- 新 Issue 通常从“待整理”开始。
- 任务清楚到可以执行后，再分配给 Agent。
- 已指定评审人时，负责人不能跳过评审，把结果直接当成已经接受。
- 接受评审可以让 Issue 完成；要求修改会把下一步交回负责人。
- Agent 运行失败不会自动完成 Issue。
- `done` 和 `cancelled` 都是关闭状态。明确重新打开后，Issue 会回到 `todo`。

<a id="boundaries" />

## 状态和负责人是两件事

改变状态不会悄悄更换负责人。进入评审后，下一项决定由评审人处理，但执行负责人
仍然会显示。

向当前负责人或评审人发出明确请求时，可以启动 Agent 回复，不必把状态当成权限
开关。日常规划仍应按上表使用状态，让看板容易理解。

<a id="examples" />

## 例子

- 发布文案读者还没确定：留在“待整理”。
- 要求和负责人都已经清楚：移到“待办”。
- Agent 在等待产品决定：标记“阻塞”，并写明由谁决定。
- 文件和检查已经准备好：移到“评审中”。
- 评审人接受结果：Issue 可以进入“已完成”。
- 请求被撤回：移到 `cancelled`。再次需要时，用评论说明原因并重新打开到 `todo`。
