<a id="definition" />

## 定义

每个 Issue 的状态都是它在生命周期中所处位置的持久信号。看板和 Agent
通过它判断当前工作需要整理、执行、评审、解除阻塞，还是已经结束。

<a id="states" />

## 状态

| 状态 | 含义 | 下一步通常由谁处理 |
| --- | --- | --- |
| `backlog` | 已记录任务，但还需要整理 | 负责规划工作的人 |
| `todo` | 请求和验收条件已经清楚 | 负责人 |
| `in_progress` | 负责人正在执行 | 负责人 |
| `blocked` | 某项明确的依赖或决策阻止了进展 | 能解除阻塞的人；这也是可评审状态 |
| `in_review` | 已有可判断的产物和证据 | 评审人 |
| `done` | 结果已接受，没有剩余必要工作 | 无，除非明确重新打开 Issue |
| `cancelled` | 工作被有意停止，且没有已接受的结果 | 无，除非明确重新打开 Issue |

<a id="constraints" />

## 约束

- 一个 Issue 只有一名负责人。相互独立的工作应拆为子 Issue 或关联
  Issue，不能给同一条记录安排多名负责人。
- 评审结论必须带评论，而且只能在 Issue 为 `in_review` 或 `blocked` 时提交。
- 负责人 Agent 尝试完成带评审人的 Issue 时，Rudder 会把状态改为
  `in_review`。这条路径只能通过评审人接受结论后完成。
- `done` 和 `cancelled` 都是关闭状态。只有评论带有明确的重新打开意图时，
  Rudder 才会把它们恢复到 `todo`。

<a id="boundaries" />

## 边界

状态不能替代负责人、执行租约、任务领取或评审。自动路由仍然受状态约束，但向当前负责人或评审人发出的明确请求可以在任意状态下运行，而且不会静默改变该状态。添加评审人不会自动把 Issue 移到 `in_review`；在普通评论中写“通过”也不会生成结构化评审结论。

`blocked` 应对应一项具体缺失条件，不是普通错误的收纳箱。工作不应继续时使用
`cancelled`；已有结果被接受时应使用 `done`。重要的状态
变更会留下活动记录，并始终受 Issue 所属组织的边界限制。

<a id="examples" />

## 例子

- 一项请求还没有验收条件，先放在 `backlog`。结果定义清楚、负责人可以
  开始后，再移到 `todo`。
- Agent 完成了带评审人的 Issue。Issue 进入 `in_review`；评审人带评论
  请求修改后，下一步回到负责人。
- 工作必须等待客户提供文件。设为 `blocked`，在阻塞评论中写明缺少的
  文件，收到后再继续。
- 一项请求在结果被接受前撤回。把它设为 `cancelled`；请求恢复时，通过带有
  明确重新打开意图的评论让它回到 `todo`。
