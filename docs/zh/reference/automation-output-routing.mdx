<a id="definition" />

## 定义

自动化输出路由决定每次执行结果由哪个工作页面承载。自定义自动化默认把结果
发送到 Chat。重复任务需要 Issue 字段和生命周期时，可以明确选择跟踪为 Issue。

<a id="states" />

## 状态与模式

| 输出模式 | 一次实际执行的结果 | 自动化运行上的来源链接 |
| --- | --- | --- |
| `chat_output` | 为这次执行新建一段 Messenger 对话 | `linkedChatConversationId` |
| `track_issue` | 新建执行 Issue，进入正常的分配和评审流程 | `linkedIssueId` |

自动化运行会记录任务是已接收、已开始、已完成、失败、跳过还是合并。即使没有
新建 Chat 或 Issue，最终状态也会保留在运行记录上。

<a id="constraints" />

## 约束

- 每次真实的 Chat 输出执行都会得到一段独立对话。Rudder 不会把某段人工 Chat
  永久作为所有后续结果的收件箱。
- 被跳过或合并的运行不会创建空对话。
- Chat 输出失败时会保留可见的部分结果或备用证据。
- 跟踪为 Issue 后，任务遵循正常的分配、状态、Agent 运行、评审和关闭规则。

<a id="boundaries" />

## 边界

输出模式不表示任务是否重要、昂贵或耗时。应根据团队需要的协作记录选择页面。
受治理的团队策略仍可以要求使用 Issue，即使结果也适合在 Chat 中阅读。

两种模式都以自动化运行为调度记录。Chat 对话不能替代运行记录，执行 Issue
也不能替代自动化定义或日程。

<a id="examples" />

## 例子

- 每日摘要适合发到 Chat，负责人可以直接阅读，并在本次执行对话中继续追问。
- 每周合规检查需要负责人、验收条件、产物和评审结论，适合跟踪为 Issue。
- 并发策略合并了一次重复触发时，应在自动化运行中查看原因，不会出现空白的
  Chat 或 Issue 占位记录。
