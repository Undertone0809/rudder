Automation output routing 决定人在哪里检查结果。

新建 custom automation 默认使用 chat output。重复工作需要 issue lifecycle 结构时，可以显式切换到 tracked issue output。

## 选择 issue output

结果需要这些东西时，用 issue output：

- assignment
- status tracking
- review
- artifacts 或 files
- follow-up work
- durable close-out evidence

Issue output 会创建 execution issue，并进入正常的 assignment、run、review 和 close-out lifecycle。应该因为需要这些结构而选择它，而不是仅仅因为工作重要、昂贵或耗时。受治理的团队策略仍然可以要求填写 issue 字段。

## 选择 chat output

希望人通过对话接收结果并继续追问或调整时，用 chat output，而不是进入结构化 issue lifecycle。

适合的例子：

- 适合继续追问的周期报告
- 希望留在同一上下文里的状态检查
- 通过对话交付的信息回复
- 适合继续调整的分析

Chat output 把 audit trail 留在 automation run 和 chat transcript 上。

每次真正执行都会创建一条与 automation run 关联的独立 Messenger conversation，不会把未来所有 run 都送进某个已有的人工 Chat。

被跳过或 coalesced 的 run 不会创建空对话。Chat-output execution 失败时，Rudder 会留下可见的部分结果或 fallback 证据，而不是静默创建空的未读线程。

## 不确定时

需要明确 assignment、status 或 lifecycle 管理时，选 issue output；希望通过持续对话交付和跟进时，选 chat output。任务重要程度和运行时长本身不决定模式。
