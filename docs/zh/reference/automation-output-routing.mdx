<a id="definition" />

每项自动化都要决定每次结果放在哪里。根据人们怎样使用结果来选择，不要只看
Agent 运行时间长短。

<a id="states" />

## Chat 还是 Issue？

| 选择 | 最适合 | 每次真实运行会创建 |
| --- | --- | --- |
| 发送到 Chat | 一个人可以在对话中阅读、讨论并完成 | 一段独立 Messenger 对话 |
| 创建 Issue | 结果需要负责人、状态、依赖、队列或评审 | 一条正常跟踪的 Issue |

两种方式都会保留自动化运行和底层 Agent 运行。

运行历史可能显示 `received`、`running`、`coalesced`、`skipped`、
`issue_created`、`completed` 或 `failed`。这些标签说明触发过程，关联的 Chat
或 Issue 仍然保留自己的任务状态。

<a id="constraints" />

## 跳过或失败时会怎样

- 被跳过或合并的触发会保留运行记录，说明为什么没有创建新工作。
- Chat 运行开始后失败，会保留已经创建的对话、部分结果或失败说明。
- Issue 运行失败时，Issue 会保持打开，方便继续处理。
- 修改结果方式只影响未来运行，不会改变旧结果。

<a id="boundaries" />

## 只保留一份任务事实

Chat 结果留在原对话，Issue 结果沿用正常 Issue 流程。Messenger 可以提醒你，
但不会成为任务的第二份副本。

即使 Chat 更方便，团队策略仍然可以要求某些受控工作必须创建 Issue。

<a id="examples" />

## 例子

- 个人每日简报：Chat。
- 需要经理接受的每周报告：Issue。
- 为支持队列创建后续工作的 Webhook：Issue。
- 一位负责人阅读并讨论的定时调研摘要：Chat。
