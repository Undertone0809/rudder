完成本页后，你会有一个组织、一个可以工作的 Agent，以及一份可以检查的结果。这里用一个示意案例说明流程：Agent 起草 Markdown 发布公告，人来评审结果。

开始前，请先[安装并打开 Rudder](/zh/get-started/installation)，准备好第一个 Agent 要使用的本地运行环境，以及保存公告的文件夹。

<a id="first-loop" />

## 1. 给组织命名

输入组织显示名称，例如“发布团队”。第一个页面只会询问名称，Rudder 会自动建立内部组织标识。目标和 Issue Key 不在新手流程里设置，之后可以在日常工作页面和设置中添加或查看。

## 2. 配置第一个 Agent

选择第一个 Agent 使用的运行环境，并完成环境检查。运行环境决定 Agent 每次运行时在哪里执行。只有必要检查通过后，Rudder 才会创建 Agent；如果页面报告配置问题，请先修复再继续。

设置完成后，Rudder 会打开 Messenger。`Getting Started` 分组已经标记为已读，不会制造虚假的未读提醒。你可以先打开欢迎内容，也可以直接完成下面的示例。

## 3. 选择 Chat 或 Issue

如果你想在一段持续对话里起草和修改公告，用 Chat。

Issue（任务单）是带有明确状态和生命周期的任务记录。需要指定负责人、跟踪依赖或安排评审时使用；评论、Agent 运行、产物和评审结论可以留在同一条记录中。

本例有明确产物和评审人，所以使用 Issue。新建任务单，并写入：

```md
标题：起草发布公告

期望结果：
产出一份可以评审的 Markdown 公告。

验收标准：
- 有简短标题
- 包含安装命令
- 解释一个具体使用场景
- 列出尚未解决的问题
```

![Issue 看板](../../images/first-organization-issue-board.png)

## 4. 让下一步可以直接执行

只有当另一个人或 Agent 不需要追问任务含义就能开始时，才把 Issue 移到 `todo`。把第一个 Agent 设为唯一负责人。因为公告需要另一位成员判断质量，再指定一位评审人。把可以执行的 Issue 分配给 Agent 后，Rudder 会自动唤醒它，不需要另外点击启动。

如果范围、优先级或验收标准还没有定，就留在 `backlog`。多项独立工作应该拆成不同 Issue，不要把同一条任务单交给两个负责人。

## 5. 检查 Agent 运行

Rudder 会调用已经配置的运行环境，并把这次有边界的执行记为一次 Agent 运行。

![Agent 运行详情](../../images/agent-run-detail.png)

运行结束后，检查以下内容：

- 运行摘要或对话记录
- Markdown 产物或它的链接
- Agent 完成的验证
- 如果未完成，是否写清阻塞原因

看不到可检查的产物时，先让 Agent 补充文件或链接，再进入评审。

## 6. 评审结果

产物准备好后，把 Issue 移到 `in_review`。评审人检查任务单、产物、运行证据和评论，然后选择明确的评审结论，并填写说明。通过后，Issue 会自动完成；要求修改时会回到负责人；选择阻塞时，原因会继续显示。

判断这条工作链是否完整，可以让另一位读者打开同一条 Issue。如果对方不用去别的工具拼凑过程，就能找到请求、Agent 运行、产物和评审结论，说明记录已经足够。

## 出错后怎么恢复

如果运行失败，保持 Issue 打开，检查运行证据，并写清下一步。缺少凭据或需要人做决定时，把任务移到 `blocked`，同时指出由谁解除阻塞。Messenger 会把这条注意力信号带回相应负责人。
