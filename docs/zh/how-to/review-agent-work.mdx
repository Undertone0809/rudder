评审只回答一个问题：真实结果是否满足任务要求？它和审批不同，审批决定某项操作
是否允许发生。

<a id="completed-state" />

## 有用的评审会留下什么

有用的评审会说明检查了什么、做出什么决定、为什么，以及下一步由谁负责。

<a id="prerequisites" />

## 开始前

Issue 应该已经有：

- 一位明确的评审人
- 可以真正打开的产物
- 清楚的验收条件
- 相关运行、检查和已知风险的链接

<a id="case-backed-steps" />

## 评审结果

1. 打开 Issue，阅读原始要求和验收条件。
2. 打开真正产出的文件、预览、报告、截图或链接。不要只看摘要就接受。
3. 检查重要事实和测试。需要知道使用了什么运行工具、是否正常结束、改了什么或
   为什么失败时，再打开 Agent 运行。
4. 逐条对照验收条件。
5. 记录一个结论，并写出具体评论：
   - 结果满足要求时，选择**接受**。
   - 负责人需要修改时，选择**要求修改**。
   - 缺少必要输入、权限或产物时，选择**阻塞**。
6. 另外的工作应创建后续 Issue，不要藏在一句模糊的通过评论里。

<a id="success-signal" />

## 检查评审记录

后来的人应该不需要打开私聊或重新拼运行过程，就能看见产物、决定原因和下一位
负责人。接受会通过评审操作关闭任务；要求修改会保留评论并把任务交回负责人。

<a id="recovery" />

## 无法判断怎么办

缺少产物或必要信息时不要接受。明确要求补充你需要的文件、来源、测试、截图或
运行详情。

如果评审发现一条会影响未来工作的经验，先保存反馈。技能或指令变更应单独提出，
说明它依据哪些例子，以及怎样测试或撤销。
