<a id="completed-state" />

## 完成后的状态

完成本页后，发布公告 Issue 会保存产物、Agent 运行证据，以及带说明的结构化评审结论，并明确下一位负责人。接受的工作已经关闭；需要修改或输入的工作仍保持打开，而且已经正确路由。

<a id="prerequisites" />

## 开始前

Issue 必须处于可以评审的状态，并且已经指定评审人。负责人应附上或链接产物、验证说明、已知风险和相关 Agent 运行。评审判断产物是否满足请求；审批则是另一项决定，用来授权受治理操作。

<a id="case-backed-steps" />

## 评审发布公告

1. 打开 Issue，重新核对验收标准：安装命令正确、宣传主张有依据、受众明确，而且交付的是 Markdown 文件。
2. 打开公告本身。不能只看运行摘要就判断产物质量。
3. 检查 Agent 运行结果、运行环境和模型、可用的成本数据、对话记录、原始证据、验证和终止状态。只有可读证据没有回答问题时，才继续查看原始日志。
4. 确认产物连接到这条 Issue 和本次运行，普通来源链接也没有被错误标成 Agent 生成的产物。
5. 填写具体说明，并记录一个结构化评审结论。满足标准时接受；需要负责人修改时要求修改；缺少必要证据或权限时选择阻塞。
6. 评审发现独立工作时，新建或链接后续 Issue，不要把它藏在含糊的接受说明中。

<a id="success-signal" />

## 成功信号

后来的人能够看见评审了什么、哪些证据支持结论、评审人为什么这样判断，以及下一步由谁负责。接受只能通过结构化路径完成 Issue；要求修改时，任务会回到负责人，评审说明继续保留。

<a id="recovery" />

## 恢复

产物或证据缺失时，不要接受。明确要求补充用于判断的文件、来源、测试、截图或运行详情。如果评审运行结束时没有结构化结论，而且 Issue 仍在 `in_review`，Rudder 可以安排次数有限的评审人跟进；自由文字回复不会自动变成接受。

评审发现可复用经验时，把反馈和证据一起保存。不要静默修改技能、Agent 操作说明、工作流或决策。沉淀前应提出明确目标、范围、评估、审批路径和回滚方法。
