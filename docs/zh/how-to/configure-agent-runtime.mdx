<a id="completed-state" />

## 完成后的状态

完成本页后，一个 Agent 已保存运行环境配置，环境测试结果已经得到解释，并且一次低风险 Agent 运行留下了可见结果或阻塞，以及对话记录或原始输出证据。

Agent、Agent 运行和运行环境仍是三个对象。Agent 承担职责，运行记录一次尝试，运行环境执行这次尝试。面向负责人的可选项见[运行环境类型](/zh/reference/runtime-types)。

<a id="prerequisites" />

## 开始前

你需要有权编辑 Agent，还要在 Rudder 实际调用的位置准备好运行环境。本地运行环境应先在同一台主机安装并登录对应 CLI；外部服务则要准备可访问端点和凭据。机密信息放在主机环境或 Rudder 的机密字段中，不要写进版本库配置。

下面用一个示意发布文案 Agent 和本地 Codex 说明。其他面向负责人的运行环境也沿用同样的验证思路，但能力并不完全相同。

<a id="case-backed-steps" />

## 配置发布文案 Agent

1. 打开发布文案 Agent 的详情页，编辑 `Runtime` 配置。
2. 选择 **Codex (local)**。默认 CLI 缺失时，Rudder 会显示设置说明，但支持自定义命令的运行环境仍可以继续填写。
3. 选择该模型支持的模型和思考强度。切换模型后，如果原强度不受支持，Rudder 会清除它。
4. 只有职责确实需要时才添加专用操作说明文件，并填写 Rudder 主机可读取的绝对路径。
5. 检查网页搜索、绕过沙箱等宽权限选项，只为确实需要这些能力的可信本地工作启用。
6. 运行 **Test runtime chain**。`pass` 表示准备完成；`warn` 是必须理解的可见提示；`fail` 表示探测失败，需要先修复。
7. 保存 Agent，再到 Chat 请它起草两行发布标题。
8. 打开对应 Agent 运行，检查实际运行环境、结果、对话记录或原始输出，以及可用的用量或成本证据。

受支持的本地运行环境会自动得到 Rudder 第一方控制工具，不要再手动添加第二套 Rudder MCP 服务。只有内置 Browser 已启用，而且这次本地运行符合条件时，Browser 工具才会出现。

<a id="success-signal" />

## 成功信号

环境测试应为 `pass`，或是限制已经理解的 `warn`。真实运行确实使用所选环境，Chat 显示完整回答或明确阻塞，Agent 运行详情则保留底层证据。只有探测通过、没有真实运行，还不能证明配置可用。

<a id="recovery" />

## 恢复

如果探测报告找不到命令，确认 CLI 已安装在 Rudder 主机，并且位于进程的 `PATH` 中；也可以填写受支持的自定义命令。身份验证失败时，先在 Rudder 外登录对应运行环境，再重新测试。操作说明文件或工作区不可读时，修正绝对路径和主机权限后再试。

如果 `warn` 在真实运行中变成失败，检查运行的终止错误和原始证据，针对具体的服务商、模型、端点或权限修复。在低风险运行成功前，不要让这个 Agent 承担周期性正式工作。
