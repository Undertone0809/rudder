<a id="definition" />

## 定义

评审判断产物是否满足请求。评审人检查 Issue、产物、Agent 运行证据和评论，再选择结构化结论，并填写必要说明。接受后可以完成任务；要求修改时回到负责人；被阻塞时，缺少的信息继续保持可见。

审批和评审不是一回事。审批授权一项受治理的操作，例如支出或敏感变更。评审可以接受产物质量，但不授权使用该产物的操作；审批也可以允许一项操作，却不判断产物质量。

反馈指出哪里做得好、哪里有错、缺少什么，或哪些做法值得重复。学习则是有意识地把这些证据沉淀到未来上下文、技能、操作说明、工作流、决策或评估案例中。

<a id="case" />

## 一个示意案例

文案 Agent 提交了发布公告。评审人认可安装说明，但要求把限制条件写得更清楚。修改通过后，团队发现每次发布评审都会检查同一项限制，于是起草发布技能变更，引用已经评审的 Issue，并先评估效果，再让后续工作使用。

<a id="when-useful" />

## 各个步骤适合什么时候使用

任务是否完成需要由负责人之外的人判断时，用评审。下一位执行者或未来运行需要理解结论原因时，留下反馈。只有某个规律已经稳定，而且能改善当前 Issue 之外的工作时，才沉淀为长期经验。

把评审工作交给评审人和真正记录评审结论，是两个不同事件。Issue 进入可评审状态，只代表下一步轮到评审人；结构化结论写入之前，工作还没有被接受。

<a id="operating-boundaries" />

## 操作边界

Issue 已指定评审人时，负责执行的 Agent 不能直接标记 `done` 来绕过评审。自由文字中的“接受”或“拒绝”可以作为证据，但不能代替结构化评审结论。评审跟进次数有边界，并继续由评审人负责。

风险最高的是静默学习。反馈不会自动改写 Agent 的长期行为。学习变更需要关联证据、明确目标和范围、合适的审批路径，以及评估或回滚方法。

具体步骤见[评审 Agent 工作](/zh/how-to/review-agent-work)。受治理操作应查阅[审批、预算和活动记录](/zh/reference/approvals-budgets-activity)。
