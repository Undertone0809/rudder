<a id="definition" />

## 定义

Rudder 划分了几种文件边界，因为背景资料、持久产物和可修改的执行目录承担的任务不同。

| 位置 | 用途 |
| --- | --- |
| Library | 人和 Agent 都可以引用的组织持久文件 |
| 项目资料 | 项目运行可以作为起始上下文使用的一组 Library 文件或外部资料 |
| 项目工作区 | 项目实际工作的代码仓库或文件夹 |
| 运行工作区 | 单次运行使用的具体文件系统与分支边界 |
| Agent 文件夹 | 单个 Agent 的操作说明、记忆、长期记录和技能状态 |
| 工作区备份 | 可检查、恢复或下载的组织工作区版本 |

项目资料是一份准入清单，不是组织中的全部文件。产物应继续连接到产生它的 Chat、Issue、运行或项目，不能只留在对话记录里。

<a id="case" />

## 一个示意案例

一个咨询团队正在准备客户简报。源笔记保存在 Library，并作为精选资料附加到项目。Agent 通过运行工作区修改项目仓库，再把最终简报保存到项目 Library 文件夹，并从待评审 Issue 中链接过去。后续运行可以找到已经接受的简报，不会连第一次尝试留下的所有草稿文件一起继承。

<a id="when-useful" />

## 各个位置适合什么时候使用

需要长期留在组织记录中的文件放到 Library。只有项目运行应默认得到某项资料时，才把它附加为项目资料。代码仓库工作使用项目工作区；改动需要明确隔离策略时，使用运行工作区。临时产物不应放进 Library，除非它属于最终证据。

在默认本地 Desktop 布局中，组织文件位于 `~/Documents/Rudder` 下的映射文件夹。映射以组织身份为准，因此修改组织名称不会悄悄移动文件。

<a id="operating-boundaries" />

## 操作边界

受保护的 Agent 操作说明、技能、运行环境托管目录和缓存路径都不是普通 Library 内容。Desktop 的本地打开操作仍要经过工作区和真实路径校验，也不会让浏览器或服务器部署获得打开本地应用的能力。

风险最高的是破坏性文件操作。已经映射的组织文件夹如果丢失，Rudder 会把它当作恢复问题，不会自动建立空文件夹覆盖现场。还有未完成 Issue 依赖运行工作区时不能归档；恢复备份前，也会先创建一份安全版本。

先查阅[工作区边界](/zh/reference/workspace-boundaries)，再按[管理工作区和 Library](/zh/how-to/manage-workspaces-and-library)操作。
