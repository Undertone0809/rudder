刚开始使用 Rudder 时，不必先建立一整套层级。只有当目标、项目或 Issue 能回答
团队真正遇到的问题时，再把它加进来。

<a id="definition" />

## 选择够用的最小单位

| 你想回答的问题 | 使用 |
| --- | --- |
| 为什么要做这些工作？ | 目标 |
| 哪些任务、对话、文件和日期属于同一件事？ | 项目 |
| 谁负责这项任务、现在到哪一步、由谁评审？ | Issue |

**目标**记录一项会持续多个任务的结果。大方向可以继续拆成较小目标。

**项目**把相关工作和资料放在一起，包括 Chat、Issue、资源、工作区、负责 Agent
和目标日期。

**Issue（任务单）**把一项较大的任务放在一个地方。需要指定负责人、跟踪依赖
或安排评审时使用；相关对话、Agent 运行、文件和评审结论会留在一起。

<a id="case" />

## 例子：发布一次产品更新

- **目标：**让新用户顺利完成第一次任务。
- **项目：**七月上手体验改进。
- **Issue：**重写快速开始、拍摄新截图、检查发布后的页面。

目标说明原因，项目汇总共同资料，每条 Issue 则让一个负责人知道接下来要交付
什么。

<a id="when-useful" />

## 什么时候不必增加结构

简短请求可以一直留在 Chat。一条 Issue 不需要单独建项目，一个项目也不一定要
新建目标。只有当关联关系能帮助别人理解工作或拿到正确上下文时，才值得添加。

<a id="operating-boundaries" />

## 需要知道的规则

- 目标、项目和 Issue 都属于同一个组织。
- 一条 Issue 只有一个负责人。不同职责应拆成多条 Issue 或子任务。
- 项目状态只用来汇总工作，不会代替 Issue 或自动化自己的状态。
- 仍有工作依赖某个目标时，Rudder 会阻止直接删除它。

完整流程见[让 Issue 从接收走到完成](/zh/how-to/issue-lifecycle)。
