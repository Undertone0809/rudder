<a id="definition" />

## 定义

目标说明一条工作线为什么存在。同一组织内的目标可以形成层级，让组织使命逐步连接到更具体的结果。

项目用来汇总相关工作和上下文。它可以把目标、Chat、Issue、资料、工作区、负责 Agent 和目标日期放在一起。项目状态只描述这组工作的整体情况，不能替代 Issue 或自动化各自的状态。

Issue（任务单）是带有明确状态和生命周期的任务记录。需要指定负责人、跟踪依赖或安排评审时使用；评论、Agent 运行、产物和评审结论可以留在同一条记录中。

完整模型见 [Issue 概念](/zh/concepts/issues)，状态含义以 [Issue 状态参考](/zh/reference/issue-statuses)为准。

<a id="case" />

## 一个示意案例

一个小团队准备发布公告。组织目标是让新用户理解这次发布。团队建立一个发布项目，把公告、截图和发布说明放在一起，再创建一条 Issue，请文案 Agent 交付 Markdown 草稿，并指定评审人。

目标解释原因，项目汇总共用上下文，Issue 则写清下一步由谁交付什么结果。

<a id="when-useful" />

## 各自适合什么时候使用

一项工作的原因需要跨越多次任务长期保留时，用目标。多件工作共享上下文、资料或结果时，用项目。下一项工作需要明确协作状态时，用 Issue。简短的对话式任务可以一直留在 Chat，不必建立任务单。

只有关系确实能帮助别人理解或执行工作时，才添加链接。不是每条 Issue 都需要单独项目，也不是每个项目都需要新目标。

<a id="operating-boundaries" />

## 操作边界

目标、项目和 Issue 都不能跨越组织边界。目标层级不能形成循环，项目链接本身不会让工作进入可执行状态，一条 Issue 也只能有一位负责人。

风险最高的是删除或解除关联。只要项目、Issue、自动化或其他工作仍依赖某个目标，Rudder 就会阻止删除，避免现有工作的理由被悄悄移走。

任务需要结构化执行时，继续阅读[让 Issue 从接收走到完成](/zh/how-to/issue-lifecycle)。
