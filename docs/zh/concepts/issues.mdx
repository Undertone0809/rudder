<a id="issue-definition" />

**Issue（任务单）**把一项较大的任务放在一个地方。需要指定负责人、跟踪依赖
或安排评审时使用；相关对话、Agent 运行、文件和评审结论会留在一起。

如果一个人可以在对话中提出要求、修改并接受结果，就把任务留在 Chat。只有当
更多参与者、步骤或决定需要协调时，再创建 Issue。

![Issue 详情](../../images/issue-detail.png)

## 一条 Issue 里放什么

- 想要的结果，以及判断结果的方法
- 负责下一步的一个人或 Agent
- 当前状态和依赖
- 评论和明确交给 Agent 的请求
- 相关的 Agent 运行记录
- 文件、截图、链接和其他结果
- 需要评审时的评审人与结论

## 用日常语言理解状态

| 状态 | 什么时候使用 |
| --- | --- |
| 待整理（`backlog`） | 还需要确定范围、优先级、负责人或结果 |
| 待办（`todo`） | 任务已经清楚，负责人可以开始 |
| 进行中（`in_progress`） | 负责人正在处理 |
| 阻塞（`blocked`） | 下一步在等待某个人、依赖、权限或外部事件 |
| 评审中（`in_review`） | 结果已经可以交给其他人判断 |
| 已完成（`done`） | 结果已经被接受 |

不要把模糊请求直接移到“待办”。新的负责人读完 Issue 后，应该不需要再问
“怎样才算完成”。

## 负责人

一条 Issue 只有一个负责人，让下一步始终清楚。两个 Agent 承担不同职责时，
应拆成多条 Issue 或子任务。

把准备好的 Issue 分配给 Agent 后，Rudder 可以自动开始工作。普通评论只会补充
信息，不会唤醒 Agent；确实需要它处理评论时，使用明确的 Agent 提及。提及不会
改变负责人。

## 评审

只有当结果需要负责人之外的人判断时，才添加评审人。产物准备好后，再把 Issue
移到“评审中”。

评审人可以接受结果、要求修改，或说明还缺什么。如果 Agent 运行失败，应保持
Issue 打开并写清下一步，不能用“已完成”隐藏失败。

## Issue 编号

`R6-42` 这类编号由组织的 Issue Key 和数字组成。修改 Issue Key 只会改变显示
方式，不会更换任务本身。使用旧 Key 的链接仍然可以打开。
