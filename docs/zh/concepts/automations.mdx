自动化把可重复的工作变成 Rudder 里的一个明确对象。它在运行前就确定 owner、触发方式、运行上下文和输出位置。

当同一个 agent 任务需要按计划运行、由人手动触发、通过 API 触发，或由 webhook 事件触发时，用自动化。

## 自动化包含什么

一个自动化会保存这些信息：

- 所属组织和 owner
- 执行工作的 agent 或 runtime
- 触发一次 run 的方式
- prompt 或任务定义
- 输出模式
- run 历史、状态和失败信息

每次自动化运行都会留下单独记录。这样你能看到它为什么被触发、有没有跑完、产出了什么，以及结果去了哪里。

## 触发方式

| 触发方式 | 适合 |
| --- | --- |
| 定时 | 周报、例行检查、维护任务、周期性分析 |
| 手动触发 | 由 operator 决定何时运行的重复工作 |
| API | 由另一个系统明确请求的工作 |
| Webhook | 由外部事件启动的工作 |

触发方式决定什么时候派发工作。自动化定义决定具体跑什么。

## 输出模式

自动化可以把结果送到 tracked issue，也可以发回 Chat：

- 需要分配、review、状态、产物或 follow-up 时，用 issue output。
- 希望 operator 通过对话接收结果并继续推进时，用 chat output。

新建 custom automation 默认选择 chat output，同时把 tracked issue output 作为可显式切换的选项。输出路径会改变人在哪里检查结果：issue output 进入正常 issue workflow，chat output 则让工作通过 automation run 和对应 Chat 保持可检查。重要程度、成本或运行时长本身不会要求使用 issue output，但团队策略可以要求受治理流程使用 issue 结构。

每次真正执行 chat output，都会创建自己独立的 Messenger conversation；automation 不会把未来每次 run 都塞进同一个人工 Chat。被跳过或 coalesced 的 run 不会创建空对话。Chat-output run 失败时，Rudder 会保留可见的部分结果或 fallback 证据，而不是留下没有内容的未读线程。

## Run 历史

每次 automation run 都应该留下可检查的证据：触发来源、当前状态、时间、结果、失败原因，以及存在时关联的 issue 或 Chat output。

这对周期性工作很重要。周报不应该只是一个来历不明的 prompt；你应该能看到它何时运行、由哪个 agent 处理、产出了什么，以及是否还需要人来 review。

## 什么时候不该用自动化

如果工作还没想清楚，不要先做自动化。结果、owner、数据源或 review 路径不明确时，先继续在 Chat 中推进，或使用 issue 结构整理工作。
