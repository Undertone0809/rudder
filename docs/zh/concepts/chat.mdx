Chat 是 Rudder 里由对话驱动的任务界面。你可以说清请求、补充上下文、选择 agent、运行工作、检查结果并继续调整方向。真实工作开始前，不需要先创建 issue。

![Chat issue 提案](../../images/chat-create-issue-proposal.png)

## Chat 和 issue 是两种工作方式

Chat 和 issue 都能把任务从请求推进到结果。选择更符合你和当前工作的方式：

| 工作方式 | 适合什么时候使用 |
| --- | --- |
| Chat | 你偏好持续对话、预计会在执行中不断调整方向，或希望请求、run 和结果都留在同一个线程里 |
| Issue | 你希望用明确的状态、owner、优先级、依赖、验收标准或结构化 review 来协调团队 |

Chat 不只适合快速问答。Chat 原生任务可以调用 Agent Run，产出可检查的结果，通过 Work manifest 保留来源和引用，并在不创建虚拟 issue 的情况下完成工作。

## 什么时候值得增加 issue 结构

创建或关联 issue 是给任务增加结构，不是把“不正式的请求”升级成“真实工作”。下面这些场景通常适合增加 issue 结构：

| 需要 | Issue 增加什么 |
| --- | --- |
| 团队责任 | 一个清楚可见的 assignee 和 reviewer |
| 计划管理 | 状态、优先级、项目、目标和依赖字段 |
| 协同管理 | 可以筛选和批量管理的共享队列 |
| 治理要求 | 必须遵守的 review、approval 或验收流程 |
| 工作交接 | 另一个人或 agent 之后可以接手的结构化对象 |

你也可以在 Chat 中关联已有 issue，不必中断当前对话。团队策略可以要求受治理的工作填写 issue 字段，但任务变长、变贵或变重要本身不应该强制转换。

## Issue 提案

当你明确让 Chat 生成 issue 提案时，把它当成 work order 来看：

- 标题是否说明结果？
- 描述是否包含足够上下文？
- 验收标准是否清楚？
- 项目是否正确？
- 初始状态应该是 `backlog` 还是 `todo`？
- 现在是否需要 assignee 或 reviewer？

批准后会创建一个结构化 issue，之后的 runs、评论、产物和评审决定可以挂在这个对象上；原 Chat 仍然是任务上下文的一部分。

## 好的使用场景

| 场景 | Chat 应该怎么做 |
| --- | --- |
| “我想改善 onboarding，但不知道从哪里开始。” | 澄清目标，然后在对话中开始推进；用户要求结构化时再生成 issue。 |
| “看这张截图，把问题修掉。” | 附加图片，检查问题，执行任务，并在 Chat 中报告结果。 |
| “这个 release blocker 应该谁负责？” | 对比 agent 能力并建议 owner。 |
| “这个 issue 发生了什么？” | 总结已有工作，不创建新 issue。 |

## 反模式

不要把 Chat 当成：

- 隐藏 backlog
- issue 状态的替代品
- 让 run 证据和产物消失在不可检查文本里的地方
- 评审决定的唯一记录
- 与 Rudder 工作对象脱节的通用聊天工具
