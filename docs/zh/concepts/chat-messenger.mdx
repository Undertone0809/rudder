Chat 用持续对话推进一件任务。Messenger 从整个 Rudder 中找出需要人回应的工作。两者属于同一套沟通系统，但职责不同。

以一份示例发布公告为例。负责人可以在 Chat 中请 Agent 起草，打开文件检查，再要求它缩短开头，最后直接接受结果。之后如果出现待评审事项、运行失败或阻塞，Messenger 会把负责人的注意力带回来。

## 先选任务入口

| 情况 | 从哪里开始 |
| --- | --- |
| 想在一段对话中探索、澄清、执行并不断调整 | Chat |
| 需要指定负责人、跟踪依赖、显示状态或安排评审 | Issue |
| 团队规则要求填写字段或进入共享队列 | Issue |
| 一位负责人可以在同一段对话中判断结果 | Chat |

Chat 和 Issue 是并列入口。Chat 不是正式工作开始前的候场区，任务耗时长或重要，也不代表必须创建 Issue。只有协作结构确实有用时，才创建或关联任务单。

![Chat 中的 Issue 提案](../../images/chat-create-issue-proposal.png)

## 让结果和证据留在任务旁边

一段 Chat 可以保留请求、Agent 运行、后续修改和最终回答。文件与链接侧栏分成三类：

- **Outputs**：Agent 确实创建，并且有附件或运行证据支持的产物
- **Sources**：负责人提供的资料，以及本次运行可用的项目上下文
- **References**：对话中引用或推荐，但并非 Agent 产出的外部内容

回答里出现的普通链接属于参考资料，不会自动变成产物。侧栏只显示当前对话的内容，不会混入同一项目中其他 Chat 的文件。

如果工作由 Issue 承载，产物和评审结论就应留在那条 Issue 上。Messenger 负责带人回到原记录，不再建立第二份决定记录。

## 精确指出回答中的一段内容

你可以选择已完成、已停止或失败的助手回答文本，也可以选择负责人可见的 **Process**
文字，把这段原文附到下一条 Chat 消息中。每条标注都可以带一段补充说明和自己的文件。
选择 **Add to chat** 会直接附上选中内容，选择 **More details** 会同时加入一条请 Agent
详细解释的提示；当来源是已完成的助手回答时，也可以选择 **Ask in side chat**。

草稿中的标注可以继续编辑。消息发送后，它会成为不可修改的消息证据。排队消息、**Steer**、
重试、编辑分支、分叉和侧聊都会保留这些标注；只要原始内容仍可用，你也可以从标注
返回来源位置。

标注属于用户引用的 Chat 上下文，不是系统指令，也不会自动变成 Issue 的评审结论或学习
证据。如果需要长期治理记录，仍应使用 Issue 和评审流程。

## Messenger 找回人的注意力

![Messenger 注意力界面](../../images/messenger-approvals.png)

Messenger 回答两个问题：现在什么需要我处理，我应该回到哪里行动？

| 提醒 | 应该回到 |
| --- | --- |
| Agent 提问 | 原始 Chat 或关联 Issue |
| Agent 运行失败 | 运行记录以及来源 Chat 或 Issue |
| 工作阻塞 | 缺少输入或负责人的原始记录 |
| 等待评审 | 带有产物的待评审 Issue |
| 等待审批 | 对应操作所拥有的审批记录 |

人的注意力集中在 Messenger，但持久状态仍属于原始对象。Messenger 不是待办队列、通用聊天应用，也不能成为评审结论的唯一记录。

## 只为当前 Chat 选择模型

输入区中的运行环境控件会显示当前 Chat 使用的模型和思考强度。修改其中任一项，只会影响这段对话后续开始的回答，不会改写 Agent 已保存的运行环境、凭据、技能、工作区或备用模型。选择 **Agent default**，可以让对应控件恢复使用 Agent 的保存值。

正在运行的回答会继续使用启动时的模型和强度。排队消息也会保留入队时显示的值，即使消息开始前又修改了对话控件。新 Chat、分支和侧聊都会重新从 Agent 默认值开始。

## Agent 回复时又发了一条消息

当前回答还在运行时，新消息会进入可见队列，不会在同一个 Chat 中并行启动第二次回答。发送前，你可以编辑或删除这条消息。

只有当前回答成功结束，排队消息才会自动发送。如果你停止回答或运行失败，消息会留在队列中等待处理。这样，一次中断的运行不会悄悄执行后续指令。
