Chat 和 Messenger 是同一套沟通系统里的两个入口：Chat 通过持续对话把任务从请求推进到结果，Messenger 把人的注意力带回正确的 Chat、issue、run 或决策。

偏好通过持续对话工作时，用 Chat。整个工作系统里有事情需要你处理时，用 Messenger。

![Messenger 注意力界面](../../images/messenger-approvals.png)

## 它们怎么配合

| 入口 | 用来做什么 | 下一步 |
| --- | --- | --- |
| Chat | 通过对话澄清、执行、调整并完成任务 | 继续留在 Chat，或在需要结构化协同时创建/关联 issue |
| Messenger | 回复、issue 线程、失败运行、阻塞、评审、预算提醒和决策 | 回到关联 issue、run 或线程，留下清楚下一步 |

边界很简单：Chat 推进工作。Messenger 让进行中的工作不丢失人的注意力。

## 什么时候给 Chat 增加 issue 结构

Chat 和 issue 是两种并列的任务工作方式，不是前后两个阶段。需要下面这些结构时，可以创建或关联 issue：

- 一个 owner 执行下一步
- agent runtime 预算
- review 或 approval
- 失败或阻塞后的恢复位置
- 未来团队需要回看的持久历史

任务仍然可以继续在 Chat 中推进。创建 issue 是增加结构化协作能力，不是让任务取得“真实工作”身份。团队策略可以要求受治理的流程填写 issue 字段。

![Chat issue 提案](../../images/chat-create-issue-proposal.png)

## Messenger 应该把你带回哪里

Messenger 回答一个很实际的问题：

> 现在什么需要我的注意，它属于哪个原生工作对象？

它应该把注意力信号变成下一步行动：

| 注意力信号 | 持久下一步 |
| --- | --- |
| Agent 提问 | 回复，并把决定留在原始 Chat 或关联 issue 中 |
| Run 失败 | 打开关联 Chat、issue 或 run，决定如何恢复 |
| 工作阻塞 | 写清楚缺少什么输入或 owner |
| 评审等待 | 接受、要求修改或标记 blocked |
| Chat 生成 issue 提案 | 接受、编辑或拒绝这个可选的结构化工作项 |

Messenger 不应该变成另一套任务系统。下一步应该回到原生承载它的 Chat、issue、run、review 或 approval。

## 反模式

不要把 Chat 或 Messenger 当成：

- 隐藏 backlog
- Chat、issue、run、review 或 approval 原生状态的替代品
- 让执行证据失去持久来源对象的地方
- 评审决定的唯一记录
- 与 Rudder 工作对象脱节的通用聊天工具
