Rudder gives agents predictable filesystem locations for shared project Library files, skills, runtime work, and agent-private state.

![Workspaces and resources](../images/workspaces-resources.png)

## Which workspace should I use?

| Use case | Location |
| --- | --- |
| Source code or project repo work | Project workspace |
| Durable reports, screenshots, exports, plans, and handoff files | Project folder in Library |
| Cross-project references and reusable docs | Shared Library files |
| Agent-private instructions, memory, and local state | Agent home |
| Temporary scratch validation | `/tmp` or system temp |

## Workspace boundaries

Use managed workspace paths instead of ad-hoc folders:

- project repositories stay in their attached project resource locations
- durable project files belong under that project's Library folder
- agent-private memory, instructions, and skills stay under that agent's home directory

## Durable outputs

When a project is created, Rudder creates a matching folder under Library:

```text
projects/<project-slug>/
  README.md
```

Agents should place durable project work files inside that project folder. They can create subfolders as the work naturally requires, such as `research/`, `screenshots/`, `proposals/`, `evals/`, or `handoff/`. Rudder does not require a fixed `plans/` folder.

Use `/tmp` only for transient scratch files and verification artifacts.

## Project resources

When a run is linked to a project, Rudder injects the explicitly attached Project Context resources into the runtime context. These resources can be external references or Library files. Library-backed resources use safe paths relative to the organization workspace root, so agents can read the file-native knowledge directly without treating protected system folders as project resources.

The Library tree also shows attached Project Context resources under the matching `projects/<project-slug>/resources/` folder. Those entries are virtual references back to the resource catalog; external repositories, URLs, and connector objects are not copied into Library.

Project Context is the curated starting point, not the full knowledge boundary. Agents can still inspect broader Library files when the attached context is not enough.

## Inspect and edit Library files

Library references can open in Rudder's Side Panel so you can inspect a file
without replacing the current Chat, issue, or Messenger route. Supported files,
including PDFs, render inline. Use **Open in Library** when you need the full
Library work surface.

Markdown files are editable in the Side Panel. Rudder autosaves against the last
confirmed version instead of silently overwriting a newer change. If another
writer changed the file first, your draft stays visible and you choose **Keep
mine** or **Use latest**.

In Rudder Desktop, the file **Open** menu can send the validated file to its
default application or a detected IDE. Folder and terminal actions use the
file's containing directory. These are local Desktop conveniences and are not
available to browser or remote deployments that cannot open files on your
machine.

## Local Desktop folders

In the default local Desktop layout, organization files live in a readable
folder under `~/Documents/Rudder/<org-folder>`. Rudder keeps the folder mapped to
the organization's stable identity, so changing the display name does not
silently move or replace the folder. If an established folder is missing,
restore it or a workspace backup instead of creating an empty replacement.

## Local development

The Rudder repository itself uses `pnpm dev` for local development. Codex-managed worktrees are auto-isolated by the dev runner; manually created worktrees should initialize an isolated worktree instance before running a second local server.
