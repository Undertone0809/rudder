Automations turn repeatable work into a defined Rudder object. They name the owner, trigger, runtime context, and output path before the run starts.

Use an automation when the same agent task should run on a schedule, from a manual button, through an API call, or from a webhook.

## What an automation contains

An automation keeps the repeatable part of the work together:

- the organization and owner
- the agent or runtime that should execute the work
- the trigger that starts a run
- the input prompt or job definition
- the output mode
- run history, status, and failures

Automation runs are separate records. That lets Rudder show what was dispatched, whether it ran, what it produced, and where the output went.

## Triggers

Rudder supports four trigger shapes:

| Trigger | Use it for |
| --- | --- |
| Schedule | Reports, recurring checks, maintenance tasks, and routine analysis |
| Manual dispatch | Operator-started repeatable work |
| API | Work started from another system with an explicit request |
| Webhook | Work started by an external event |

The trigger decides when work is dispatched. The automation definition decides what work should run.

## Output modes

Automations can route output into a structured issue or a chat conversation:

- Use issue output when the result needs assignment, review, status, artifacts, or follow-up work.
- Use chat output when operators should receive and continue the result through a conversation.

New custom automations default to chat output, with tracked issue output available as an explicit alternative. The output path matters because it changes where people review the result: issue output enters the normal issue workflow, while chat output keeps the work inspectable through the automation run and its chat conversation. Importance, cost, or run length alone does not require issue output, although team policy may require issue structure for governed workflows.

Each real chat-output execution gets its own Messenger conversation; an automation does not reuse one human chat for every future run. A skipped or coalesced run does not create an empty conversation. If a chat-output run fails, Rudder keeps visible partial or fallback evidence instead of leaving a silent empty unread thread.

## Run history

Each automation run should leave inspectable evidence: dispatch source, current state, timestamps, result, failure reason when it fails, and linked issue or chat output when one exists.

This is useful for routine work. A weekly report should not be a mystery prompt. It should show when it ran, what agent handled it, what the result was, and whether a person needs to review anything.

## When not to use automation

Do not use an automation for work that still needs shaping. Continue in Chat or use issue structure first when the outcome, owner, data source, or review path is unclear.
