Chat is Rudder's conversation-driven task surface. You can explain a request, attach context, choose an agent, run the work, inspect results, and keep refining the task in one conversation. You do not need to create an issue before real work begins.

![Chat issue proposal](../images/chat-create-issue-proposal.png)

## Chat and issues are two ways to work

Both Chat and issues can move a task from request to result. Choose the style that fits you and the work:

| Work style | Use it when... |
| --- | --- |
| Chat | You prefer an ongoing conversation, expect to adjust direction as the agent works, or want the request, run, and result together in one thread |
| Issue | You want explicit status, ownership, priority, dependencies, acceptance criteria, or structured review across a team |

Chat is not limited to quick questions. A chat-native task can invoke Agent Runs, produce inspectable outputs, preserve sources and references in its Work manifest, and reach a finished result without a synthetic issue.

## When issue structure helps

Creating or linking an issue adds structure; it does not turn an informal request into “real work.” Consider issue structure when you want:

| Need | What an issue adds |
| --- | --- |
| Team ownership | One visible assignee and reviewer |
| Planning | Status, priority, project, goal, and dependency fields |
| Coordination | A shared queue that can be filtered and managed in bulk |
| Governance | A required workflow for review, approval, or acceptance criteria |
| Handoff | A structured object another person or agent can pick up later |

You can also link an existing issue without leaving Chat. A team policy may require issue fields for governed work, but task length, cost, or importance alone should not force a conversion.

## Issue proposals

When you ask Chat to draft an issue proposal, review it like a work order:

- Does the title name the outcome?
- Does the description include enough context?
- Are acceptance criteria clear?
- Is the project correct?
- Should it start in `backlog` or `todo`?
- Does it name an assignee, or explicitly explain why it should stay unassigned?
- Does it need a reviewer now?

Approving a proposal creates a structured issue that future runs, comments, artifacts, and review decisions can attach to. The source Chat remains part of the task context.

## Good use cases

| Use case | Chat behavior |
| --- | --- |
| "I need to improve onboarding, but I am not sure where to start." | Clarify the goal, then begin the work conversationally or propose issues if the user asks for structure. |
| "Use this screenshot and fix the problem." | Attach the image, inspect the problem, execute the task, and report the result in Chat. |
| "Which agent should own this release blocker?" | Compare agent capabilities and suggest an owner. |
| "What happened in this issue?" | Summarize existing work without creating a new task. |

## Anti-patterns

Avoid using Chat as:

- a hidden backlog
- a replacement for issue status
- a place where run evidence and outputs disappear into uninspectable text
- the only record of a review decision
- a general-purpose chat app disconnected from Rudder work
