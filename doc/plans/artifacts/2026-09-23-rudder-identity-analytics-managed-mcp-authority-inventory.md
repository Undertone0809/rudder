## Authority test

The authority is the component that admits the operation, authenticates the actor, chooses the organization or installation scope, writes the durable state, owns the transaction or migration, schedules recovery/maintenance, and determines fallback or process exit. A protocol crate, generated bundle, client helper, or staged binary is not an authority merely because it exists or is invoked.

- **External provider**: the provider source-of-truth service is outside this repository; that does not make an in-repository Rudder service external.
- **N**: Node/Electron currently owns the product policy, durable state, listener, transaction, or lifecycle.
- **M**: Node/Electron owns orchestration and durable product policy while a bounded native helper is called.
- **P**: Rust is protocol-only or a pure helper; it has no production state owner, DB writer, auth provider, or public listener for this row.
- **U**: a plausible Rust surface exists, but no first-party production caller carrying this authority was established.

The client pins HTTPS outside loopback development in `desktop/src/identity-client.ts:88-97` and validates token/device/account responses at `:107-150`.
- **Rudder account binding.** `identity/src/handler.ts:512-564` takes the verified external principal, resolves or creates the stable first-party user with `packages/identity-db/src/account-linking.ts:29-170`, and records `supabase_auth_user_binding` plus the resumable migration ledger. A normalized-email advisory lock prevents duplicate Rudder subjects. This is first-party Identity ownership even though the root principal and provider session are external.
- **Device and session state.** `identity/src/handler.ts:1733-1887` issues, approves/denies, and redeems the device code; `:1894-2016` performs the browser PKCE authorization-code, access-token, and refresh-token flows. `packages/identity-db/src/device-authorization.ts:116-259,342-464` persists hashed device codes and row-locked decisions; `desktop-authorization.ts:29-290,321-520` consumes authorization codes transactionally, creates or updates the installation device, issues hashed access/refresh credentials, records `device.session.created`, and reads auth epochs. `packages/identity-db/src/schema.ts:97-180,212-298` owns device codes, devices, access/refresh credentials, authorization codes, and server-exchange codes. - **Server exchange and offline grants.** `identity/src/handler.ts:2024-2079` resolves a device access credential, issues a one-time server exchange code, and consumes it with installation/audience checks. `packages/identity-db/src/server-exchange.ts` owns the transactional code/JTI consumption. `identity/src/runtime.ts:47-84` loads the Identity-owned Ed25519 signing keys; `handler.ts:671-709` emits offline grants carrying account/device/installation/auth-epoch state. `identity-db/src/auth-epochs.ts` and `schema.ts:411-426` are the durable invalidation boundary.
- **Profile and device management.** `identity/src/handler.ts:2230-2358` resolves an account principal, lists devices, reads or updates the account avatar, and revokes a device. `packages/identity-db/src/account-profile.ts:12-44` reads and updates the first-party `identityUsers` row; `device-authorization.ts` and the device credential tables enforce installation/user scope. ### Rust boundary and retirement status

`packages/identity-core` is TypeScript, not Rust: it provides normalization, secret hashing, offline-grant signing/verification, and telemetry assertion helpers (`packages/identity-core/src/*`). `native/crates/auth-core/src/lib.rs:1-5,112-333` is limited to signed short-lived actor envelopes and a process-local replay guard; it does not contact an Identity provider, persist credentials, create local sessions, own installation claims, or open a listener. `native/crates/server-foundation/src/lib.rs:1082-1101` reports `public_listener: false` and `product_write_authority: false` and describes a trusted Node bridge. No Rust production caller for the Identity listener, provider/device/token flows, `rudder_identity` DB/migrations, consent/recovery jobs, or local account bridge was found in this source checkpoint.

Current default is therefore **N + external provider**: the in-repository Node/TypeScript Rudder Identity service owns its listener, `rudder_identity` durable state, device/desktop/server-exchange protocol, profile, telemetry consent/assertion, migration gates, and recovery lifecycle; Supabase Auth and configured Google/GitHub remain true external provider authorities for root web authentication. Rust status is **P**, not a login/session migration. Node/Electron cannot retire for this surface until a Rust service owns the Identity listener/serverless contract, provider/device/token/session flows, local binding and migration transactions, offline replay/recovery, consent synchronization, actor/installation propagation, external-adapter fallback behavior, and the same local bridge contract. No Rust default or production caller for that authority was found in this source checkpoint.

## Smallest next complete authority unit

The smallest coherent next unit is the **standalone product analytics collector service**, bounded to its own HTTP listener, `rudder_analytics` schema, three DB roles, Identity assertion/consent boundary, ingest/consent state, maintenance projector/retention, aggregate-only report, migration ledger, and startup/shutdown contract. It is a complete service boundary with no need to move the main Rudder server, local account bridge, or managed MCP in the same change. A Rust ingest-only handler is smaller in code but is not a complete authority because Node would still own consent, projections, retention, report privacy, migrations, and lifecycle.

### Real acceptance for that unit

The acceptance must use a disposable PostgreSQL instance with separate collector, rollup, reader, and migration roles and a real loopback HTTP listener. It must establish the following before any Node retirement claim:

1. Apply the analytics migration ledger from a clean database and prove schema/table privileges: collector can ingest/update its allowed rows, rollup can project/delete, reader can read only rollups/quality/privacy aggregates, and reader cannot read raw events, subjects, or installation rows.
2. Start the Rust service in required mode with the exact Identity key/issuer/id fixture. Exercise anonymous and account-linked assertion paths, missing/expired/wrong-installation assertions, consent sync/revoke, monotonic consent epochs, and cross-installation/subject rejection.
3. Submit valid, malformed, oversized, future, late, duplicate, and same-event-id/different-payload batches. Read back accepted, duplicate, conflict, rejected, quality-counter, installation last-seen, and payload digest state. Run concurrent duplicate submissions and prove only one durable event wins.
4. Restart after the initial maintenance pass and during projector/retention. Prove deterministic rollups, work-loop revision projection, threshold suppression, retention deletion, installation/subject deletion, and no stale aggregate leakage.
5. Exercise the report endpoint with valid and invalid windows and secret, verify aggregate-only output and privacy suppression, and prove the reader role cannot bypass the API boundary.
6. Verify clean SIGTERM/SIGINT shutdown, startup failure exit, required-mode failure closed, no Node collector listener or migration/job caller in the accepted process graph, and the Desktop uploader's retry/ack contract against the Rust service.

Until that evidence exists, the correct default remains Node. The acceptance is proposed here, not performed by this inventory.

- This is a source inventory on d328, not a full semantic inventory, percentage claim, test/build result, runtime acceptance, production verification, release readiness, or Node-retirement proof.
