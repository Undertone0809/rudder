## Goal and boundary

Move existing-cookie resolution for no-Bearer HTTP requests entering the managed Rust public ingress to Rust. Keep Better Auth issuance, OAuth/device/login/logout and other auth lifecycle routes as explicit Node bridges. Keep WebSocket cookie resolution on Node. Keep Board API keys, `pcp_` bearer resolution, agent keys/JWT and their established precedence unchanged. In required mode, a syntactic `Bearer ` takes the existing bearer path and never attempts cookie auth; otherwise native resolution is authoritative even when the cookie is absent, malformed, expired, revoked, or the database is unavailable. Optional/local-trusted mode preserves `local_implicit`; it does not treat an arbitrary cookie as authenticated.

Named public acceptance routes are synthetic `GET /api/auth/get-session` and `GET /api/orgs/:org_id/members/directory`. The same no-Bearer signed result must also reach proxied business routes so Node can build the existing Board actor without calling Better Auth/local session resolver again. Node still queries `instance_user_roles` and active memberships on each request; Rust does not mint/freeze permissions. A session assertion is request authentication (which principal, or authoritative none), not a payload-specific authorization grant.

## Private assertion threat model

The public ingress proxy deletes caller-provided session-assertion headers before any Node hop. Rust creates exactly one short-lived assertion (target <=30 seconds) for the request outcome (`authenticated` principal or authoritative `none`) over a domain/version, fixed audience, exact method, exact raw path+query, issue/expiry, random request id and nonce, session id/user id (no credential/token). Use deterministic unambiguous payload encoding, HMAC-SHA256, and constant-time verification; the distinct HMAC key is required only for native session delegation and is never the listener/upstream key, cookie secret, or actor-envelope key. The Node private listener must bind loopback in required mode; the Rust upstream remains fixed numeric loopback. The Node replay registry is capped at 50,000 entries and uses a 64-slot expiry wheel; ordinary proof validation checks one nonce in the map, while expiry cleanup visits elapsed buckets and each accepted entry is removed once. The assertion is internal and must never appear in a response/log. Node validates/consumes the assertion before any route side effects, then sets the actor or authoritative `none`; it never reads caller assertion fields as identity. Required protected requests with missing/invalid proof fail closed and never call `resolveSession`.

The body is intentionally not included: the assertion authenticates the session principal, not a particular payload. The external client controls its own body as an authenticated caller; business routes retain their normal schema/permission/approval checks. The private Node hop is trusted loopback; a same-host process able to observe that hop is outside this assertion's threat model. Do not imply that this assertion protects payload bytes from a compromised local process.

Configured Better Auth session and dont_remember cookies are removed from ordinary business hops so Node cannot silently resolve them; unrelated cookies remain forwarded. Auth lifecycle bridge paths retain cookies so Better Auth/local signout/issuance behavior remains Node-owned. Bearer requests keep bearer precedence; the native session assertion is never minted or trusted when a syntactic Bearer header is present. Exact `/api/auth/get-session` with Bearer stays on the established Node bearer path; without Bearer it is native. Node must not use session fallback for `/get-session` in required native mode, including direct-to-private-listener requests.

## Cookie/session semantics and linearization

- Better Auth is pinned at 1.6.23 and depends on better-call 1.3.7. Cookie name is `better-auth.session_token` or `__Secure-better-auth.session_token`, Path=/, HttpOnly, SameSite=Lax; no Domain. Select only the configured name and exact effective BA secret. Duplicate cookies are first-occurrence-wins in the pinned better-call `parseCookies` implementation: it inserts a name only when the Map does not already contain it. The current Desktop local resolver also returns the first matching occurrence. Both native modes therefore use first-occurrence-wins. Evidence inspected at `/private/tmp/better-call-source/v137/package/dist/cookies.mjs` (the `parseCookies` loop and `utils.mjs::tryDecode`) and `server/src/services/local-account-auth.ts:160-171` (cookie lookup); regression vectors put conflicting values in both orders. Malformed percent encoding is mode-specific: Better Call `tryDecode` preserves the original text, while Desktop's `decodeURIComponent` returns no cookie. BA expiry is strict `expiresAt < now`. Verify the separately signed `better-auth.dont_remember` value; any truthy verified string skips refresh. Cookie behavior must match BA in this mode.
- BA table is `session(id, token, user_id, expires_at, created_at, updated_at)` joined to `user`. Default TTL 7 days/update age 24 hours. Refresh when `expiresAt - 7 days + 24 hours <= now`, unless valid truthy `dont_remember`; then set `expires_at=now+7d`, `updated_at=now`. Expired BA sessions are deleted durably (`expiresAt < now`). Preserve current public response cookie behavior: existing wrapper discards Better Auth Set-Cookie headers; do not introduce renew/clear cookie headers.
- Desktop local account uses configured local HMAC secret only and exact cookie prefix; current local resolver duplicate-cookie semantics are first matching occurrence wins, expiry `<= now`, no refresh and no delete. Issuance uses fixed 30 days (offline grant expiry can shorten it). This secret is separate from BA secret and may rotate each process startup. Never fallback between secrets or modes.
- Use a DB row lock to linearize lookup/refresh/delete against signout/revoke. Revoke committed before the session row lock/read => deny; resolver locking first => that in-flight request may finish; refresh never recreates a deleted row. BA expiry cleanup and refresh are in one transaction. Directory authorization starts/rechecks after any waited session write/lock and uses one repeatable-read snapshot for session existence, current user, current admin/membership, and directory data. A membership/admin removal committed before that snapshot denies; removal after snapshot may finish the admitted read.
